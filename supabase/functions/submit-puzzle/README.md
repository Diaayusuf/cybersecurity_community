# `submit-puzzle` Edge Function

Local M6 implementation. It is not deployed. This is a public anonymous submission endpoint, not an authenticated-user API.

## Request

`POST /functions/v1/submit-puzzle`

Headers: `Content-Type: application/json`, `apikey: <configured public publishable key>`. Do not send a service-role/secret key from the browser. The Supabase function’s `verify_jwt` is disabled only for this endpoint because the current page has no user session; the handler checks the publishable key itself. This key check identifies the public application component, not the player.

Allowed JSON fields only:

| Field | Rules |
|---|---|
| `challenge_id` | Lowercase slug: letters/digits followed by letters/digits/underscore/hyphen; max 64. Current route uses `main`. |
| `answer` | Non-empty string, trimmed, case-sensitive; max 256 server characters. The current input has a 30-character UI limit. |
| `player_name` | Required trimmed display name, 1–40 characters. It does not prove identity. |
| `domain` | Optional trimmed text, max 40; blank becomes null. |
| `idempotency_key` | UUID generated by the browser’s secure random API. |

The body is capped at 8 KiB. Extra fields (including correctness, score, rank, identity, timestamp, or IP) are rejected. The submitted answer is processed in memory and never logged or sent to the database RPC.

## Responses

| Status | Meaning |
|---|---|
| 200 `incorrect` | Incorrect answer; no verified solve. |
| 201 `verified` | Correct answer; returns only server-generated solve ID and timestamp. A matching idempotent retry returns the same response. |
| 400 / 413 / 415 | Invalid JSON/fields, excessive body, or wrong content type. |
| 401 / 403 | Missing/unrecognized publishable key or disallowed browser origin. |
| 404 | Unknown/inactive challenge; same generic response. |
| 409 | Normalized display name already has a solve for the challenge, or idempotency key was reused with changed input. |
| 429 | Per-source limit reached; response includes bounded `Retry-After`, without counters. |
| 503 | Secret, network, runtime, or database failure; retry without assuming success. |
| 405 | Unsupported method; `Allow: POST, OPTIONS`. |

`OPTIONS` is a 204 CORS preflight response. Allowed origins are exact values from the server secret; wildcard origins are rejected. CORS is not authentication.

## Server-side controls

- `CYBERX_CHALLENGE_CONFIG_JSON` is a server secret containing the challenge map and active state. The real expected answer belongs only in the Dashboard’s Edge Function Secrets. No answer is in this repository’s sample/test data.
- `CYBERX_ANSWER_HMAC_KEY`, `CYBERX_RATE_LIMIT_HMAC_KEY`, and `CYBERX_IDEMPOTENCY_HMAC_KEY` are independent random secrets with at least 32 bytes each. Never log or commit them.
- `CYBERX_ALLOWED_ORIGINS` is a comma-separated allowlist of exact origins, with no path or trailing slash. Add only the production site and explicitly approved local/test origins.
- The function reads the server-side Supabase URL and service credential from the platform environment (`SUPABASE_SECRET_KEYS`, or legacy `SUPABASE_SERVICE_ROLE_KEY`). It calls only the two named RPCs; the service role has no direct M6 table grants in the migration.
- Source limiting is 8 requests per fixed 10-minute window across all challenges for one source. Supabase documents the first `X-Forwarded-For` entry as the client address. The function validates it, HMACs it, stores no raw address, and fails closed if missing. This is not a defense against distributed abuse. Do not accept an IP JSON field or add this header to browser CORS permissions.
- Idempotency is scoped by challenge, keyed before storage, and retained for 90 days. Same-key changed payloads conflict. One trimmed/case-insensitive display name per challenge is enforced by a unique database constraint; names are not authenticated identities.
- Client responses and logs contain no answers, digests, secrets, raw addresses, or database error details. The handler intentionally emits no request/body logging.

## Local development

The full Supabase local stack requires Docker and a Deno Edge Runtime. In a local environment with the prerequisites installed:

1. Start a disposable local Supabase stack and apply the local migrations using current CLI help.
2. Create an ignored `supabase/functions/.env.local` containing only synthetic challenge data, random local HMAC keys, the local origin, and local platform settings. Do not copy production answers or credentials.
3. Run `supabase functions serve submit-puzzle --env-file supabase/functions/.env.local`.
4. Exercise the local function with a synthetic request. Browser integration must rewrite all Supabase URLs to the local stack; never let a local regression test fall through to the production project.

This workspace had no Deno or running local Supabase/Docker runtime. The included Node tests mock the PostgREST RPC responses, and Playwright intercepts external services; they are not staging/database integration tests.

## Deployment and rollback

Deployment is outside this local task and requires separate owner approval. This repo has no remote link or staging credentials. Verify CLI help and the target explicitly; current CLI v3 uses `--remote=<ref>` for hosted database operations and Edge Function deployment.

In a disposable staging project, provision synthetic-only secrets, then use the current CLI help to confirm flags. Deploy the endpoint first while the existing frontend still uses its current flow, then preview the ordered migrations. After all staging checks pass, publish the static frontend last:

```powershell
npx.cmd --yes supabase@latest db push --remote=<staging-project-ref> --dry-run
```

After a separate approval to apply staging migrations, omit `--dry-run` and retain the CLI’s interactive confirmation. Deploy the function to staging using its explicitly scoped target and per-function JWT setting before applying M6:

```powershell
npx.cmd --yes supabase@latest functions deploy submit-puzzle --remote=<staging-project-ref> --use-api --no-verify-jwt
```

This ordering lets the function become available before M6 removes browser table-write access; the new frontend is published only after the endpoint and migrations are ready. Production requires a separate approval, production-specific secrets/origin, migration review, and release window. Never add `--yes` to bypass hosted confirmation.

Do not restore anonymous direct INSERT as a rollback. Preserve the verified table and historical data; prefer forward fixes. If the function is unavailable, the frontend reports a retryable error and does not claim success.
